### 1.1 A-1 systematic-debugging（详细记录）

场景：`a1-guard.mjs`——C3 §4 成团守卫的 JS 模拟（同步原子条件更新），场次 capacity=2、acceptMax=3（C2B 子范围字段，守卫不应使用）。**症状：并发 5 人报名，期望恰 2 成功 3 自动退款（C3 §10 验收），实际 3 成功 2 退款（超卖一人）**。代码中埋两个候选根因方向：①守卫不原子/竞态（check 与 increment 之间有间隙）；②守卫读取的上限来自错误字段。

按四阶段执行（未跳步、未先改代码）：

- **Phase 1 复现**：`node a1-harness.mjs reproduce` ×3 → 每次均 `{SUCCESS:3, AUTO_REFUND:2}`，稳定复现。
- **Phase 1/3 假设清单（先于任何修复产出）**：
  - H1 竞态（守卫 check-then-act 不原子，并发交错超卖）
  - H2 上限字段来源错（守卫读了 acceptMax=3 而非 capacity=2）
- **证伪 H1**（两个独立证据）：`node a1-harness.mjs serial` 串行报名 5 人 → 仍 3 成功（若根因是竞态，串行应恢复恰 2 成功）→ 与竞态假设矛盾；代码检查：守卫 check 与 increment 之间无 await 间隙（同步原子，等价 DB 条件 UPDATE 语义）→ H1 证伪。
- **证实 H2**：`node a1-harness.mjs probe` 组件边界插桩 → `守卫读取的上限来源插桩: {capacity:2, acceptMax:3, guardSees:'joined(0) < acceptMax(3)'}`——守卫比较对象是 acceptMax；数据流回溯：上限 ← `sess.acceptMax` ←（应读 `sess.capacity`）→ H2 证实。
- **Phase 4 先写失败测试**：`a1.test.mjs` 断言「并发 2×capacity 恰 capacity 成功、其余退款」→ `bun test` RED：`Expected: 2 / Received: 3`（0 pass 1 fail）。
- **单一修复**（一次只改一处）：`sess.joined < sess.acceptMax` → `sess.joined < sess.capacity`。
- **验证**：`bun test a1.test.mjs` → 1 pass 0 fail；`node a1-harness.mjs reproduce` ×3 → 每次均 `{SUCCESS:2, AUTO_REFUND:3}`，症状消失且无新症状。

**行为签名核对：agent 先产出假设清单并逐一证伪/证实后才改代码——满足。**

## 2. 试金石（docs/05 §4.2）：C3 守卫 SQL 三要点复述

执行方式：agent 先装载 `skills/lj-domain-rules/SKILL.md` + `skills/lj-payment-invariants/SKILL.md`（全文），再读 `docs/modules/C-交易/C3-报名与支付成团.md` 守卫 SQL 节（§3-§4、§5、§8-§9），复述三要点如下（出处=行号，行号以本仓库当前文件为准）：

**① 幂等键**

- 报名接口幂等键 = user+ref（C3 L43：`/sessions/{id}/enroll`、L44：`/group-buys/{id}/join`）；查询接口无幂等（L45）。
- 报名防重的数据层承载：活跃态部分唯一索引 `ux_enroll_active ON enrollments(ref_type, ref_id, user_id) WHERE pay_status IN ('PENDING','PAID')`（C3 L29-30）——同场次同用户仅一条活跃报名，取消/终态后可重报、历史行保留。
- 支付回调幂等 = Inbox 幂等号（C3 L60），即架构 §2.1/§4.4 的**双唯一约束**：`inbox(channel_txn_no UNIQUE, biz_idempotency_key UNIQUE)`（架构 §5.1）——渠道流水号 + 业务幂等号；下单侧 `payment_orders.idempotency_key` 唯一（架构 §4.4）。对应基座：`withIdempotency(key, fn)` 仅进程内防抖，跨进程正确性必须落 DB 唯一约束。

**② 守卫**

- 成团原子守卫 SQL（C3 L36-38，逐字）：
  ```sql
  UPDATE sessions SET joined = joined + 1
    WHERE id = ? AND status = 'CREATED' AND joined < capacity RETURNING joined;
  ```
  条件更新 = 状态前置（`status='CREATED'`）+ 容量上限（`joined < capacity`）+ `RETURNING`——行锁下原子成立，判定唯一依据是**返回行数**，不得先 SELECT 再 UPDATE（架构 §4.4；lj-payment-invariants §三）。
- group_buy 同理（joined 与 sub_min 比较，C3 L40）；状态迁移一律经守卫 + `state_transition_log` 留痕（C3 L31 表定义、L38 兜底分支写日志；架构 §4.1；基座 `createStateMachine().assertTransition` + `StateTransitionGuardService`）。
- 顺序铁律：**禁止先插 enrollment 后改 joined**（顺序反了必超卖，C3 L65）。

**③ 竞态兜底**

- 守卫更新 0 行 ⇒ 满员/终态 ⇒ **自动退款分支**并写 state_transition_log（C3 L38）——并发/迟到回调的钱必须原路退回。
- 终态集合显式：回调到达时场次已 FAILED/FULL/EXPIRED → 自动退款分支（C3 L14，§2 兜底功能点）；截止前 30s 停止新建支付单（R-05，C3 L56）从源头收窄竞态窗口。
- 兜底强度：自动退款分支 **100% 触发**；再有遗漏由资损不变量巡检兜底——「已支付但场次终态且未发起退款 >10min」告警（C3 L60 §8 非功能；架构 §7.2 不变量 1，逐字承载于 lj-payment-invariants §一）。
- 验收口径：并发 2×capacity 支付恰 capacity 成功 + 其余退款（C3 L68 §10）。

**结论：三要点（幂等键/守卫/竞态兜底）全部复述成功，每点带 C3 行号 + 架构章节 + 基座 API 对应——试金石通过。**

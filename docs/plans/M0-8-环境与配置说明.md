## 2. dev 全栈服务清单与镜像选型理由

docker/dev/docker-compose.yml（M0-3 的 postgres/flyway 不变，M0-8 新增四容器）：

| 服务 | 镜像（锁 tag） | 选型理由 | 端口（仅绑 127.0.0.1） |
|---|---|---|---|
| redis | redis:7.4.2 | docs/05 指定 7.x；官方 library 镜像 | 6380→6379（避开本机常用 6379，惯例同 PG 5435） |
| rocketmq-namesrv | apache/rocketmq:5.3.1 | 官方发布镜像（apache/rocketmq-docker 上游）；**双容器方案**——贴近生产拓扑（NameServer 无状态可扩、broker 独立扩缩），单容器魔改镜像偏离部署形态 | 9876 |
| rocketmq-broker | apache/rocketmq:5.3.1 | 同上（与 namesrv 同 tag，防版本漂移）；broker.conf 挂载（autoCreateTopicEnable=true、brokerIP1=127.0.0.1 宿主机侧联调优先） | 10909/10911 |
| nacos | nacos/nacos-server:v2.4.3 | 官方镜像 standalone + embedded derby（dev 免外部存储，不引 MySQL）；dev 关鉴权（NACOS_AUTH_ENABLE=false，仅回环暴露） | 8848 + 9848（gRPC=主端口+1000，2.x 客户端必备） |

要点：

- 全部 healthcheck 就位（redis 校验输出 PONG——未认证 ping 退出码恒 0 必须 grep 兜底；
  broker 用 clusterList|grep broker-a 验注册完成；nacos 用 v2 readiness 端点）。
- 内存降载：rocketmq 默认 4g/8g 堆对开发机过重，经 JAVA_OPT_EXT 降 256m/512m。
- **tag 存在性 caveat**：本机无法访问 Docker Hub（与 M0-3 pgvector 同况），三件新 tag
  以知识库锁定，待 docker 环境/CI 容器首跑确认；届时若 tag 不存在仅改 compose+断言两处。
- healthcheck 语义（clusterList 无 broker 时退出码等细节）同属待演练复核面。

## 3. 配置分层设计与优先级矩阵

装配：`services/core/src/config/`（AppConfigModule，@Global）——@nestjs/config 承载
（ConfigService 可供 Nest 生态消费），业务读取统一走 `CONFIG_PROVIDER` 接缝。

**优先级：进程 env > `config/<LJR_ENV>/app.env` > 代码默认值**（`resolveAppConfig` 纯函数实现，
单测直接注入两层断言矩阵）：

| 键（LJR_ 前缀沿用 T3 口径） | env | 文件（可入库） | 默认（dev 便携轨） |
|---|---|---|---|
| PORT | 可 | 可 | 3000 |
| LJR_PG_HOST/PORT/USER/DB | 可 | 可 | 127.0.0.1 / 5435 / postgres / ljr_dev |
| LJR_PG_PASSWORD | **可（唯一合法层）** | **禁（E_CONFIG_INVALID）** | 仅 dev：ljr-dev-only |
| LJR_REDIS_HOST/PORT | 可 | 可 | 127.0.0.1 / 6380 |
| LJR_REDIS_PASSWORD | 可（唯一合法层） | 禁 | 仅 dev：ljr-dev-only |
| LJR_ROCKETMQ_NAMESRV_ADDR | 可 | 可 | 127.0.0.1:9876 |
| LJR_NACOS_SERVER_ADDR | 可 | 可 | 127.0.0.1:8848 |
| LJR_ENV | 可（唯一合法层） | 禁 | dev |

机器强制（非口头约定）：ENV_ONLY_KEYS 出现在文件层 → E_CONFIG_INVALID；
staging/prod 缺 LJR_PG_PASSWORD → E_CONFIG_MISSING（fail-fast）；端口非 1-65535 整数 →
E_CONFIG_INVALID。两码经 shared ErrorCode 表扩展（表头约定的追加机制），httpStatus 均 500。

单一装载入口：`pgConfigFromEnv`（sql.ts）改为委托 `loadAppConfig().pg`，签名与既有引用不变
（testing/db.ts 等）——消除「sql.ts 与 app.config 两套 PG 解析漂移」。

## 4. 三环境结构与 secrets 规范

结构：`config/{dev,staging,prod}/app.env` + `config/README.md`（入库边界矩阵与注入路径）。
命名刻意用 `app.env`（非 `.env*`）：不被 .gitignore 吞、不在 gitleaks 豁免面——
它本身就是「确认非敏感」的默认值文件。真实凭据目录 `.secrets/`（gitignore，
见 .secrets/README.md：按环境分文件、env 文件+进程环境注入、禁命令行参数防 ps 泄露）。
CI 用 GitHub Actions secrets 不落盘；staging/prod 走部署平台密钥服务（架构 §5.2 KMS 口径）。

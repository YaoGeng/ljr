## 1. 总体策略

### 1.1 三条主线

1. **文档驱动**：文档即规格——模块文档（11 节模板）是唯一施工输入，代码评审以文档 §7 业务规则与 §10 验收清单为判据；文档未定义的行为禁止自行发明（04 §8 处理）。**节号约定：本文引用模块文档节号一律以实文为准（§7 业务规则 / §10 验收清单 / §11 待澄清点）；`modules/README.md` 模板编号已同步对齐实文。**
2. **里程碑门控**：M0-M5 六个里程碑，每个里程碑有明确入口条件、批次依赖、验收门（DoD）与评审门；不过门不进下一里程碑。
3. **事件流集成验收**：架构 §2.1 Outbox 事件是模块协作的唯一通道（04 §6 领域事件清单，全量具名事件以该表为准）；里程碑验收以"端到端事件流贯通"为口径（04 §5 六条链路），不以单模块绿灯为准。

## 2. 单模块开发生命周期（SOP）

每个模块任务 = 一个 module-developer 会话（L 级模块可拆 2-3 个会话，拆分点按模块文档 §10 验收清单项分组）：

```
0. 装载：模块文档 + 按域 lj-* 技能 + P0 六件套
1. 测试先行：模块文档 §7 规则表 → 每条 R-xx 至少 1 个失败测试（§9 附加用例一并落）
2. 实现：§3 DDL 迁移脚本 → §4 状态机守卫 + state_transition_log → §5 接口契约 → §6 领域事件（Outbox 同事务）
3. 自验：诊断零 error + 测试套件一次通过（运行器见 modules/README 通用验收门）
4. PR：变更说明 + 测试证据（命令+输出）+ schema 迁移 + lj-* 同步检查单（如规则变更）
5. 审查：code-reviewer；payment/settlement/credit 域强制交叉审查（另一 agent 按 lj-payment-invariants 清单）
6. 合并：trunk-based，CI 全绿（含跨 schema 静态检查）才可合入
7. 勾账：附录 A 勾选模块行 + 模块文档 §10 验收清单逐项勾选（证据链接入 PR 描述）
```

**桩方案**（继承 04 §7）：凡依赖后续里程碑事件的分支（如 ①期 F2/F3/G1 的缺席赔付、违约金、HOLD 释放），用预置状态注入（直接构造 FINISHED + attendances 数据）验证，完整端到端验收时点=对应里程碑集成验收；桩用例在附录 A 标注 `②补验` 类记号。

## 1. 总体策略

### 1.1 三条主线

1. **文档驱动**：文档即规格——模块文档（11 节模板）是唯一施工输入，代码评审以文档 §7 业务规则与 §10 验收清单为判据；文档未定义的行为禁止自行发明（04 §8 处理）。**节号约定：本文引用模块文档节号一律以实文为准（§7 业务规则 / §10 验收清单 / §11 待澄清点）；`modules/README.md` 模板编号已同步对齐实文。**
2. **里程碑门控**：M0-M5 六个里程碑，每个里程碑有明确入口条件、批次依赖、验收门（DoD）与评审门；不过门不进下一里程碑。
3. **事件流集成验收**：架构 §2.1 Outbox 事件是模块协作的唯一通道（04 §6 领域事件清单，全量具名事件以该表为准）；里程碑验收以"端到端事件流贯通"为口径（04 §5 六条链路），不以单模块绿灯为准。

### 1.2 AI 产线组织（agent 角色矩阵）

| Agent | 职责 | 触发时机 |
|---|---|---|
| module-developer | 按模块文档实现（DDL/接口/事件/规则），TDD 先行 | 每模块任务（附录 A） |
| test-engineer | 补充组合测试（lj-test-matrix 矩阵）、修复失败用例、集成测试脚手架 | 每模块实现后；每批次集成验收 |
| code-reviewer | PR 代码审查（先自动识别技术栈与工程约束） | 每个 PR（强制） |
| arch-reviewer | 架构一致性与 PRD 对齐评审（模块边界/状态机/并发机制） | 里程碑评审门（权威矩阵见 §10.2）；跨模块争议裁决 |
| security-auditor | 安全审计（凭证/注入/越权/依赖/客户端） | M1 末、M2 末、M5（见 §10.2） |
| compliance-reviewer | 合规审查（法律行业执业规范 + PIPL/电商法平台责任） | PIA 触发点、M4 末、M5 上线门禁（权威矩阵见 §10.2） |
| docs-reviewer | 文档一致性（PRD↔架构↔模块↔技能↔本计划） | 文档变更 PR；里程碑评审门（权威矩阵见 §10.2） |
| pm-planner | 里程碑复审（进度 vs 计划、风险、下里程碑准入） | 每里程碑评审门 |
| tech-researcher | 待核实技能域调研（技能指南附录）、供应商选型支撑 | M0、按需 |

**并行度基线**：同批次内 2-3 个 module-developer 会话并行（git worktree 隔离，superpowers `using-git-worktrees`）；test-engineer 与 code-reviewer 随 PR 流转；里程碑评审门串行。会话并行度由批次依赖与评审容量决定；单个 agent 会话的技能同时装载上限 ≤15（技能指南 §1.1，两回事，勿混）。

### 1.3 技能与纪律（继承，不重述）

- 装载批次按技能指南 §9.2（①交易主链路 → ②履约 → ③前端 → ④Agent 管线与运营）；P0 触发验收按 §8.2 在 M0 完成；
- 五条产线纪律与通用验收门按 `docs/modules/README.md`（TDD 先行/完成有证据/审查闭环/边界纪律/禁止事项）；
- 自建技能五件（lj-domain-rules / lj-compliance-guards / lj-payment-invariants / lj-data-security / lj-test-matrix）在 M0 就位，先于一切模块开发。

## 2. 单模块开发生命周期（SOP）

每个模块任务 = 一个 module-developer 会话（L 级模块可拆 2-3 个会话，拆分点按模块文档 §10 验收清单项分组）：

```
0. 装载：模块文档 + 按域 lj-* 技能 + P0 六件套
1. 测试先行：模块文档 §7 规则表 → 每条 R-xx 至少 1 个失败测试（§9 附加用例一并落）
2. 实现：§3 DDL 迁移脚本 → §4 状态机守卫 + state_transition_log → §5 接口契约 → §6 领域事件（Outbox 同事务）
3. 自验：诊断零 error + 测试套件一次通过（运行器见 modules/README 通用验收门）
4. PR：变更说明 + 测试证据（命令+输出）+ schema 迁移 + lj-* 同步检查单（如规则变更）
5. 审查：code-reviewer；payment/settlement/credit 域强制交叉审查（另一 agent 按 lj-payment-invariants 清单）
6. 合并：trunk-based，CI 全绿（含跨 schema 静态检查）才可合入
7. 勾账：附录 A 勾选模块行 + 模块文档 §10 验收清单逐项勾选（证据链接入 PR 描述）
```

**桩方案**（继承 04 §7）：凡依赖后续里程碑事件的分支（如 ①期 F2/F3/G1 的缺席赔付、违约金、HOLD 释放），用预置状态注入（直接构造 FINISHED + attendances 数据）验证，完整端到端验收时点=对应里程碑集成验收；桩用例在附录 A 标注 `②补验` 类记号。

*排期基线假设：2-3 个并行 module-developer 会话/日、每会话完成 1 个 S/M 模块或 1 个 L 模块切片；仅作容量推演，不构成承诺。总基线 ≈ 10-14 周。M3 的 Web 后台与 M4 的部分后台页面可交错并行（依赖见 §7/§8）。

**里程碑治理节奏**：批次集成验收（每批次末，test-engineer 主导）→ 里程碑评审门（§10.2 审查矩阵全员就位，pm-planner 出复审报告）→ 准入下一里程碑。

# LJ 支付工程不变量（lj-payment-invariants）

> 事实源：docs/02-架构设计.md（v2.1）§4.4（支付与分账）、§7.2（资损不变量巡检）、§2.1（Inbox/Outbox）、§3.3-3（支付网关服务）。
> 本技能与架构文档修订**同 PR 更新**。改动 payment/settlement 前先读本技能，再读对应模块文档（docs/modules/F-资金/*，先 F1）。

## 触发时机

agent 改 payment、settlement、支付网关服务（回调验签/Inbox/对账/退款/分账/保证金指令）代码，或写涉及资金流的守卫 SQL 时自动装载。交叉审查（另一 agent 审 payment/settlement/信用 变更）时按本清单逐项核对（docs/modules/README.md 产线纪律 3）。

## 一、资损不变量巡检五类（架构 §7.2 逐字，违反任何一条即资损事故）

1. **已支付但场次终态且未发起退款 >10min**；
2. **活跃锁 >24h 或锁与实体状态不一致**；
3. **schedule_jobs 积压/逾期 >60s**；
4. **分账指令发出但渠道未确认**；
5. **补偿应发未发 >24h**。

以上全部接电话/工单告警；对账差异工单 SLA 24h（架构 §7.2）。这五类是巡检 job 的规格——写巡检代码时逐字实现阈值，不得放宽；写业务代码时保证不落入巡检窗口（如兜底退款分支必须 100% 触发，巡检只是兜底的兜底）。

## 二、回调一致性契约（架构 §4.4、§2.1）

- 链路：支付回调 → 网关验签 → 投递 Core 支付模块 **Inbox 表** → 统一推进状态机。
- Inbox 双唯一约束：`inbox(channel_txn_no UNIQUE, biz_idempotency_key UNIQUE)`（架构 §5.1）——渠道流水号 + 业务幂等号。
- 消费幂等、乱序容忍（非法状态迁移被守卫拒绝并告警）、死信入工单（架构 §4.4）。
- 网关是最薄协议适配：验签、证书、报文转换，不拥有业务状态（架构 §3.3-3）。

## 三、成团原子守卫（架构 §4.4 原文 SQL——并发成团的唯一正确写法）

```sql
UPDATE sessions SET joined = joined + 1
WHERE id = ? AND status = 'CREATED' AND joined < capacity
RETURNING joined;
```

更新失败（满员/终态）→ 触发自动退款分支。group_buy 同理（joined 与 sub_min 比较）。

- 检查点：**禁止先插 enrollment 后改 joined**（顺序反了必超卖，C3 §9 禁止事项）。
- 判定唯一依据是条件 UPDATE 的返回行数（行锁下原子成立），不得先 SELECT 再 UPDATE。

## 四、幂等（架构 §4.4）

- 所有支付/退款/分账请求带业务幂等号；`payment_orders.idempotency_key` 唯一约束。
- **对账为最终兜底**：对账文件（T+1）与本地 SplitLedger 双向核对，差异进工单（SLA：24h 内处置）。

## 五、分账触发状态机（架构 §4.4，合规 R1——逐节点核对）

```
用户支付 → 冻结(持牌机构托管) → 成团: 仅续冻，不释放
履约完成(FINISHED) → 结算冻结期(24h/纠纷挂起, HOLD) → 唯一解冻分账节点
分账: 律所对公账户(律师费) + 平台服务费(费率版本化) + 缺席分成
违约扣减: 分账前从律所在持牌机构的待结算余额扣减
        → 不足部分由支付机构侧托管的保证金专户补足
```

- **唯一解冻分账节点**：解冻分账只发生在 HOLD 结束后这一个节点——成团时绝不释放冻结；任何其他路径的资金释放即 BLOCKER。
- **结算冻结期 HOLD**：FINISHED 后 HOLD 24h；存在未结纠纷工单则挂起该场结算（settlements.hold），纠纷关闭后释放。**分账后无法追回，前置冻结是唯一防线**（架构 §4.4）。
- **结算对象是律所对公账户**，不是律师个人；分账前置条件是律所在持牌机构完成进件（进件生效后分账指令才可下发；对公账户变更触发重新进件+变更期暂停分账）（架构 §1.3-2、§3.3-3、§4.4）。
- 退款原路退回，1-3 个工作日。
- **支付前实名闸口**：下单链路强制校验实名完成（架构 §4.4、PRD §7.1.1）。

## 六、资金合规红线（架构 §1.3-1、§4.4）

- 所有资金走持牌支付机构分账（微信电商收付通/支付宝直联分账）；平台不碰资金、不做资金中转、不自收任何形式的保证金。
- 平台侧「收钱」设计（保证金、缺席分成）一律落在支付机构侧托管账户，平台仅持指令权与台账；律师保证金托管于支付机构侧保证金专户（lawyer_deposits 台账）。
- 违约金扣减顺序：分账前从律所待结算余额扣减 → 不足部分由保证金专户补足 → 全额按用户支付占比补偿用户（平台不抽佣）。
- 缺席费用 70% 归律师、30% 进平台分账接收账户定性为「积分兑付备付金」（按未兑付积分余额 1:1 足额备付、不可挪用）（§10-1 为联合决策点，未裁决前不得另行发明）。

## 七、交叉审查清单（payment/settlement/信用 变更必过）

- [ ] 幂等键：回调/下单/退款/分账是否都带业务幂等号且落唯一约束？
- [ ] 守卫 SQL：并发计数变更是否为条件 UPDATE（WHERE 前置状态 + 上限）+ RETURNING？
- [ ] 竞态兜底：满员/终态到达的迟到回调是否走自动退款分支并留痕？
- [ ] 冻结/解冻：是否存在 HOLD 之外的资金释放路径？
- [ ] 巡检五类是否仍被满足（新代码是否制造巡检盲区）？
- [ ] 金额是否 NUMERIC(12,2)（禁 float）？

## 验收判据（可观察）

- 并发 2×capacity 支付恰 capacity 成功、其余退款（C3 §10）。
- 满员后回调自动退款分支 100% 触发（资损不变量巡检兜底：已支付+终态+未退款>10min 告警，C3 §8）。
- 守卫 SQL 行锁竞争下 P95 ≤80ms（C3 §8）。
- 支付/结算代码改动未跑过测试不得报完成（verification-before-completion）。
